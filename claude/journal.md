## 2026-08-26

- Added `scratch/render-segment.ts`, an ad hoc single-clip testing script (not part of the app) built for faster iteration during review: runs the full download → transcribe → analyze → render pipeline once and picks a candidate segment by simple keyword-matching against the analyzer's `reason` text, rather than `smoke-test.ts`'s fixed `SEGMENT_INDEX`. Used throughout this and the following session's review to target specific segments on request (e.g. "show me the skill issues rant").
- Diagnosed and fixed a real subtitle bug: Whisper occasionally transcribes the same phrase twice — once as a burst of near-zero-duration words crammed into a fraction of a second, then again normally-paced a few seconds later. The existing timestamp normalization didn't drop these, it just spread the burst into ~1s of rapidly-flashing (but still shown) subtitles. Added `dropDuplicateBursts()` in `transcribe.ts` to detect and drop a contiguous run of 3+ near-zero-duration, near-zero-gap words before normalization runs (verified against the exact case that surfaced it).
- Chased a separate subtitle-desync report (fine for ~12s into a clip, then progressively ~1s late) through several rounds:
  - Initial theory: drift tied to Whisper's internal ~30s processing-chunk boundary. Tried anchoring each Whisper *segment's* words to that segment's own reported start/end (segment-level timestamps come from decoding, not forced-alignment, so seemed more trustworthy). **Reverted after testing** — Whisper segment boundaries turned out to routinely include several seconds of silence padding not actually spoken, so force-stretching words to fill them introduced new desync on top of not reliably fixing the original issue.
  - Directly tested whether the "~30s boundary" theory itself holds up: checked segment boundaries and duration-anomaly words against every 30s mark across a full ~980s video. No periodicity at all — offsets ranged ±10s with no clustering near zero. **Theory refuted**; there's no fixed seam to correct for.
  - Conclusion: it's the same general Whisper forced-alignment imprecision documented elsewhere in [bugs.md](bugs.md), just the subtle, non-bursty residual that slips past the existing duration cap — no anomaly-based fix found. Also likely responsible for an observed end-of-clip audio bleed (the padding math trusts word timestamps that can be a touch off from the true acoustic onset). Left open, deprioritized at user's direction — see [bugs.md](bugs.md) for the full trail.

## 2026-08-28

- Diagnosed a segment-selection diversity problem: across ~10 analyzer runs on the same video, a small "core" set of moments (spinner intro, recent-tab bit, a level/a player, ascending-difficulty, dislikes rant, closing teaser) came back as a candidate almost every time, while other well-reasoned candidates elsewhere only surfaced inconsistently — meaning a future multi-clip batch would likely keep regenerating the same handful of shorts. Logged in [backlog.md](backlog.md#batch-segment-selection-clusters-on-the-same-handful-of-moments).
- Implemented the code-level fix (chosen over prompt-tuning, which was judged too easy for the model to deprioritize): `diversifySegments()` in `analyze.ts` greedily reorders the analyzer's ranked candidate list so picks are spread across the video (90s minimum gap between selections) before falling back to pure engagement order once no further diverse pick remains. Verified against real analyzer output — reordered list went from clustering to spanning the full video breadth on the first pass.
- Cleaned up accumulated scratch render output (~318MB across 13 old test-clip folders) per user request; `scratch/` is gitignored so no repo impact.

## 2026-08-29 to 2026-08-31

- Switched to a second test video (`https://youtu.be/VIDEO_ID`) at user request.
- Found and fixed a real download-accuracy bug: a requested extraction range (e.g. `233.3s-259.0s`) sometimes came back containing content from up to ~15s later in the source video. Traced to `downloadSegment()`'s use of yt-dlp's `--download-sections` on a video that fell back to non-fragmented progressive-HTTP delivery (surfaced by `[GetPOT]` token-fetch warnings) — that format's section-download estimates a byte offset for a timestamp, which drifts when real bitrate varies. Fixed by no longer trusting yt-dlp's section-estimate at all: added `downloadFullVideo()` (fetch the whole video once) and `extractSegment()` (trim the exact range locally with ffmpeg, frame-accurate). Verified against the exact previously-offset range.
- That fix surfaced a much bigger, previously-masked problem: even with correct extraction, a clip could still audibly cut off mid-word deep into unintended content. Root-caused to Whisper's word-level timestamps carrying several-second-scale error — not the "usual milliseconds" this project's other fixes were tuned around, and severe enough to shift which real content a clip's boundaries actually captured, not just subtitle display timing.
- Two more fix attempts on that timestamp error, both tested and found insufficient:
  - Splitting the full-video transcription into independently-processed chunks (90s, then 30s) with a known additive time offset, on the theory that error accumulates with how much audio Whisper has processed in one continuous call. Didn't meaningfully reduce the error even at 30s chunks — three separate "should be accurate" reference measurements of the same word disagreed with each other by up to ~4s, pointing to inherent Whisper attention-timing imprecision rather than a cumulative-depth effect.
  - Discussed (not implemented) alternative free ASR options; landed on **WhisperX**, run locally via a Python subprocess rather than Groq's hosted `whisper-large-v3`.
- **Set up local WhisperX end-to-end**: installed Python 3.11 (the machine only had an unusable Microsoft Store Python 3.7 stub), a dedicated venv at `whisperx-venv/`, PyTorch with CUDA (hit and fixed a gotcha where pip silently substitutes a CPU-only torch build to satisfy a bare version pin — needed the exact `+cu128` build tag), and WhisperX itself. Wrote `whisperx_transcribe.py`, invoked as a subprocess from a rewritten `transcribe.ts` (Groq client parameter removed — transcription no longer touches Groq's API at all). WhisperX re-times every word with a dedicated wav2vec2 phoneme-alignment model rather than trusting Whisper's own attention-based timestamps.
- **Verified the fix directly against the same reference case**: the word that was ~3.6s off under Groq's full-video pass landed within ~0.03s of the tightly-scoped ground-truth position under WhisperX — on the same full, unchunked video, no chunking needed. The real boundary computation shifted by 5.3s as a result. Confirmed end-to-end on an actual rendered clip: user-confirmed both sync and the clip's ending held up correctly.
- Updated [bugs.md](bugs.md), [backlog.md](backlog.md), and [architecture.md](architecture.md) to reflect the new WhisperX-based transcription step, its new local-dependency risks (Python/CUDA setup, VRAM, model download size — all outside the Node dependency tree), and a known gap left behind (the Groq-era confidence-based hallucination-dropping mitigation isn't yet ported to the WhisperX path).
