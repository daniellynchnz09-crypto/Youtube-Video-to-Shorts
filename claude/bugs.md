# Known issues

Part of the [YouTube Short Splitter](../Claude.md) doc set. Grouped by issue rather than by time — see [journal.md](journal.md) for the chronological version.

## Open / watching

- **Confidence-based hallucination dropping isn't ported to the WhisperX transcription path.** The Groq-era mitigation for Whisper hallucinating a phrase onto unclear audio (see Resolved below) relied on Groq's per-segment `avg_logprob`/`no_speech_prob`, which the current `whisperx_transcribe.py` wrapper doesn't currently extract or expose. WhisperX's word timing is far more trustworthy now (see the drift entry in Resolved below), but a hallucinated *phrase* is a content error, not a timing one, and nothing currently guards against it on this path. faster-whisper's underlying segment objects (used internally by WhisperX before alignment) do carry the same confidence fields, so re-adding this should mean extending the wrapper's output rather than a new detection approach. Not yet done — deprioritized since the far more severe drift issue is what's been driving user-visible bugs.
- **Titles invent stakes / difficulty the content doesn't have:** the title model tends to hype a clip — calling an easy daily level's obstacle section an "Impossible Challenge" when the level is actually a lower difficulty tier and the speaker is only struggling because they aren't a strong player (user example, 2026-09-08). The transcript describes a struggle; the model reads that as high difficulty. The glossary now carries real difficulty framing per level so the model has grounds not to hype — titles that still overstate difficulty are a legitimate defect to flag.
  - **Review status:** titles were exempt from critique 2026-09-02 (the model lacked context); as of **2026-09-08** the user considers them fair to critique as rigorously as clip selection and subtitles, now that the game glossary feeds the title prompt. See [spec.md](spec.md#title-generation-context).
  - **Context layers shipped:** source-video metadata (2026-09-02) and the game glossary (2026-09-08) both feed the title + analyzer prompts — see [spec.md](spec.md#title-generation-context). Measured: mis-transcribed proper nouns corrected, and per-level difficulty framing now available to the model.
  - **Still a known weaker area:** even with context, the free Groq model over-eggs titles. Longer-term: manual title editing in the review UI (step 3), [Learn from user title edits](backlog.md#learn-from-user-title-edits), [on-screen analysis](backlog.md#game-specific-context-terminology--asset-recognition), and moving just the title step to the Claude API.
  - Concrete transcript-only nuance the model gets wrong: a piece of content compared to the top of a difficulty ranking is not itself necessarily at the top — it can sit well inside a tier while being compared upward.
  - **Related failure — mechanic errors + burying the hook.** On a clip whose payoff was an account-milestone reveal, the model titled it around an in-level mechanic it misdescribed (naming a passive object as something actively "unlocked") and pushed the actual milestone — the one thing that mattered — to the back of the title. The clip selection itself was fine; the title was the whole problem. User's fix favored a single plain statement of the milestone itself (2026-09-08). Lesson: prefer the single plainest statement of the clip's payoff over stacking level name + mechanic + milestone into one line.
  - **Burying the hook, recurrence (2026-09-09):** a clip whose actual content was "a level is inspired by an older game outside the channel's game" got titled around the clip's incidental closing action (deleting checkpoints) instead of that fact — same shape as the milestone example above, different video. User's fix: state the actual interesting fact plainly ("I learn that [level] is inspired by [reference]"). Confirms this is a recurring model tendency, not a one-off.
  - **Two more distinct failure modes (2026-09-15 review, second test video) — prompt rules added, retested, did NOT fix either one.** (1) A title stacked two unrelated beats from the same clip into one line ("I Spot a Green Orb and Figure Out Why the Level Is Called '[level]'") when the green orb noticing and the level-name realization weren't actually connected — user's note: focus a title on one aspect, don't list things that happen. (2) A title stated a cause that wasn't the speaker's actual one — "Skipping a Hidden Orb Leaves Me Fed Up with [level]" picked an incidental aside as the reason for frustration, when the transcript's own stated reason was the level's length and the speaker going nowhere on it ("I think just because it is so long...", "I think it's probably because I'm actually going nowhere"). Added three new prompt rules in `titles.ts`, then **regenerated both titles 5 times total across two rounds of prompt wording** (`scratch/titles/title-retest-k7ods3vjrOo.ts`): case (1) reliably still frames the green orb as causally revealing the level's name in every regeneration ("The green orb reveals/shows why..."); case (2) reliably still leads with "after/missing a hidden orb" as the stated cause every time, never the level-length reason actually given in the transcript. Traced likely cause of (1): the analyzer's own `reason` field for this segment already narrates the two beats as one connected "discovery" moment, and that reason text is fed into the title prompt as grounding — added a caveat telling the model to verify the reason's implied connections against the transcript, which didn't change the outcome either. Same "free model doesn't reliably follow a semantic-judgment prompt rule" pattern documented elsewhere in this doc; the prompt rules are left in (harmless, may help on other clips) but this specific pair of failure modes should be considered an accepted limitation of the free model for now, same as the difficulty-hype entry above — see its longer-term fix list (manual title editing, learning from edits, moving the title step to the Claude API).
- **Residual subtitle desync / dropped words on interjections — actively diagnosed 2026-09-09, two distinct root causes found, neither has a clean fix.** First chased 2026-08-26 (see [journal.md](journal.md)): a clip fine for ~12s then progressively ~1s late, refuted against the ~30s Whisper chunk-boundary theory, concluded to be residual forced-alignment imprecision — no anomaly-based fix found, left open at user's direction. Two new reports (2026-09-09), both on reaction interjections in the same footage, were each traced to real WhisperX output plus direct audio inspection (`ffmpeg silencedetect` on the source audio, not just the word timestamps):
  - **Whisper's ASR step, not alignment, silently drops a word.** Raw words.json shows `"Oh"` spanning 331.71-333.21 (1.5s — way too long for that word alone) immediately followed by a 1.41s *pure gap with zero words* before `"boy,"` at 334.62 (heard as "Oh boy, it's like [level]"; user reports "something" spoken in there that never appears as a subtitle at all). `ffmpeg silencedetect` on that exact window found **no silence** — the audio is continuously non-quiet throughout. Since forced-alignment can only re-time words Whisper's ASR already produced, a stretch with real non-silent audio and zero output words means the ASR step itself dropped a whole phrase — a deletion error, not a timing error. Alignment-side fixes (the existing mitigations) can't touch this.
  - **Forced-alignment misplaces an isolated interjection by ~6s when it's not anchored by nearby words.** The single token `"Ah!"` (350.13-350.23) sits inside a much longer near-silent stretch — the next word doesn't start until 359.44, a 9.2s gap. User reports the real "Ah!" is audible ~6s later than where it's rendered. `ffmpeg silencedetect` on this window confirms it isn't clean silence either (game sound effects throughout at every threshold tried, -25dB to -35dB) — meaning a naive silence-based re-snap would be unreliable here too, since a game SFX blip is acoustically indistinguishable from the real interjection to simple amplitude detection. A reliable fix would need actual voice-activity detection (distinguishing human speech from game audio), not just an energy/silence heuristic — a materially bigger addition than anything tried on this bug so far.
  - **Recommendation:** both mechanisms are confirmed, but neither has a low-risk fix — tuning Whisper's ASR sensitivity to catch more dropped words risks reintroducing the hallucination problem already fixed the opposite way (see Resolved below), and a proper VAD subsystem for the second case is a real engineering investment for a residual, edge-case-only symptom (isolated reaction sounds specifically, not normal continuous speech). Deprioritizing again unless it starts showing up outside interjection-in-long-gap cases.
  - Unrelated observation from the same review: a single exclamation duplicated by the ASR (rather than dropped or mistimed) would also slip past `dropDuplicateBursts()`, since that detector only drops a contiguous run of **3+** near-zero-duration words (see Resolved below) — not confirmed to have actually occurred here, but worth knowing the gap exists.
  - **Cross-video confirmation (2026-09-09, second test video):** the same isolated-word-near-a-gap pattern reappears in a completely different video — a lone `"I"` (505.98-506.08) followed by a 1.42s gap before the sentence actually continues, and a `"than"` stretched to 1.50s duration followed by a 1.16s gap. Confirms this isn't specific to one video/footage type; still no fix pursued, same reasoning as above.
  - **Third instance (2026-09-15, same second test video, different clip):** user-reported recurrence of the exact same pattern — an isolated `"I"` and `"than"` rendered in the wrong silence gap, then not shown again when the word is actually spoken. Same clip range as the 2026-09-09 cross-video confirmation above (the words are in the same source video), now seen by the user directly in a rendered short rather than just in raw transcript inspection. Three confirmed occurrences prompted actually building the VAD fix (see below) rather than deprioritizing again.
  - **VAD implemented and partially fixes this (2026-09-15).** WhisperX already runs a pyannote voice-activity-detection model internally to chunk audio before ASR, and the model file ships locally with the package (no download/token needed) — it just wasn't exposed. Added a standalone VAD pass in `whisperx_transcribe.py` (reuses the same model, unchunked) that outputs real speech-segment intervals alongside the words; `transcribe.ts` now cross-checks every word's timestamp against them. Investigated this exact "than" case directly: raw VAD segments show real speech in that area stops at 516.25s, but "than" (516.11-517.61, already capped to the existing 1.5s ceiling) was still bleeding ~1s into genuine silence past that. Added `clampWordsToSpeechSegments()`: clamp a word's end to the nearest VAD segment's end (+0.3s padding for VAD boundary imprecision) when a word already overlaps a VAD segment at its start but overruns past where real speech actually stops. **Verified against the real data**: re-tested the exact "than" case — corrected end moved from 517.61s to 516.55s, matching the VAD boundary; checked impact across the whole video and only 10 of 2419 words (0.4%) were touched, every one an abnormally long duration (0.4-1.1s) pulled back down, no unrelated words affected (`scratch/vad/test-clamp-impact.ts`, gitignored).
  - **The "I" case turned out to be intentional, not a bug — user correction (2026-09-15).** Investigated directly: VAD shows one continuous 503.41-508.93s (5.5s) real-speech stretch spanning both "I" (505.98-506.08) and "have" (507.50), with ~1.4s of genuinely spoken audio in between carrying no transcribed words. Read at the time as an ASR-drops-content defect (the same shape as the entry above) — **user clarified this specific case is intentional, for subtitle readability**: not every syllable of a natural, pause-heavy stretch needs its own word entry, and the existing subtitle-clearing-during-a-pause behavior (see Resolved below) already handles the visual gap cleanly. The actual reported defect (a word rendered in the *wrong* gap, then never shown again when actually spoken) is a different, narrower shape than "a stretch of speech has below-average word density." Added `logLikelyDroppedWordGaps()` anyway as a diagnostic (flags a VAD speech segment ≥1s with <50% word coverage; doesn't change output) — it found 13 such stretches across the video, but per this correction, a flagged stretch is a candidate to check, not a confirmed defect; most are likely this same benign pattern. Only worth deeper attention on a stretch a user actually reports as visually broken.
  - **Not addressed by this pass:** the original "Ah!" case (a word's *start* placed ~6s away from where VAD says the real speech is, i.e. genuinely mislocated rather than just running too long) — the video that case was found on isn't in the current audio cache, so the relocate-to-VAD-segment logic that would fix it hasn't been verified against real data yet, and per this project's verify-before-shipping practice it wasn't added blind. `clampWordsToSpeechSegments()` deliberately leaves a word alone when its start falls outside every VAD segment, rather than guessing where to move it.
- **Segment strung together from multiple long silent gaps reads as disjointed, not one moment.** Found via direct evidence (2026-09-09/14, second test video): a 36.6s candidate was 27.4s (75%) dead air across two gaps (17.0s and 10.4s) bridging three short, only loosely-related lines, and — separately — opened on the very last word of an unrelated prior sentence ("attempt.") instead of its own sentence's start. The analyzer prompt already inlines `‖pause Xs‖` markers for gaps ≥0.6s, so the model had explicit visibility into both long pauses and picked the segment anyway — there was no rule telling it multiple long internal pauses are a red flag on their own.
  - **Dead-air case, prompt rule alone didn't work:** added an explicit rule in `analyze.ts` against segments strung together from multiple ~5s+ pauses, then re-ran the analyzer on the same video (2026-09-14) — the model picked this exact segment again anyway, still 27.4s (48% of a longer 56.5s version) dead air across the same two gaps. Same "free model doesn't reliably follow a rule even with an explicit signal" pattern as elsewhere in this doc. **Actual fix:** "how much of a segment is silence" is mechanically measurable, unlike a coherence judgment call, so added a deterministic code-level rejection instead of trusting the prompt — any segment whose gaps ≥3s sum to more than 35% of its total duration is dropped outright in `groqSegmentAnalyzer.analyze()`, the same "don't trust the model, verify in code" pattern as the start/end boundary snapping.
  - **Fixed (bad-start case) + a related token-budget bug it uncovered:** `startWordIndex` had no correction at all (unlike `endWordIndex`, which already gets two layers — `snapEndIndexToPause`, `findSentenceEnd`). Added `snapStartIndexToSentenceStart()`, walking backward from the LLM's pick to the nearest real sentence start; verified directly against this exact case (correctly recovers "Wonder" from "attempt."). Trying to reproduce this fix's effect surfaced a second, worse 413 (9873 tokens) on the same video — caused by the `WIDER_MARKER_INTERVAL` fix from 2026-09-09 (see Resolved below), which turned out to be the wrong lever entirely: measuring the actual prompt showed the real chars/token ratio is ~2.7-2.9 (not ~4), and the fixed rules/instructions text alone is ~8000+ characters paid on every call regardless of video length — widening markers saves only a few hundred characters, nowhere near enough. Replaced it with real chunking (`chunkWordRanges` in `analyze.ts`): transcripts over 1300 words are now split across multiple `requestSegments` calls (100-word overlap so a boundary-straddling segment isn't missed by both sides), each comfortably under the 8000-token cap, with `MARKER_INTERVAL` back to a fixed, tighter 10 for every video. This also removes the tradeoff this bullet originally flagged (wider markers costing boundary precision) rather than just accepting it.
- **Segment cuts off right before a setup's payoff — reclassified, not actively pursuing.** A clip built anticipation ("let's find out what I'm doing today") and ended right there. Two escalating prompt-rule attempts (up to a "Critical" mandate with a matching example) didn't change the model's pick across three re-runs on the identical segment — likely because that specific payoff (a real-time spinner animation) sits outside or right at the edge of the 60s budget, per the user's own read of the footage (2026-08-20), not because the model is ignoring the rule. Dialed the rule back to a soft preference rather than a hard requirement, since forcing it too strongly risks worse picks elsewhere. Not worth more prompt tuning on the free model for now; revisit only if it turns out to recur on segments where the payoff genuinely is close by.
  - **Note:** a 2026-08-31 report initially attributed to this category ("cuts off at random," landing mid-word deep into a later sentence) turned out to actually be the Whisper timestamp-drift bug (see Resolved below) — the *analyzer's* chosen word was a clean sentence end, but the *time* assigned to it by Whisper was wrong enough that extraction landed somewhere else entirely. Now that drift is fixed, re-confirm before attributing a future "cuts off randomly" report to this entry rather than a possible drift regression.
  - **Related (2026-09-09):** a "new weekly content drops" candidate (26s) was judged too short to let the described reaction (frustration at a level feeling harder than expected) actually play out — the segment ended before its own payoff had room to land, same underlying "clip doesn't fit its arc in budget" shape as this entry, just on the short end (a strict floor of 15s let something too small through) rather than the long end.
- **Segment picked with no real content — just setup/transition, nothing happens.** User-reported (2026-09-15, second test video): a candidate covering the speaker quitting one level and opening the next was mostly menu navigation and an announcement, cut off right before any gameplay started — clean sentence boundaries, on-topic-ish, but nothing actually occurs in it. Distinct from the "cuts off before the payoff" entry above (that's about a real moment's resolution being excluded by the boundary; this is about there being no moment in the segment at all, boundaries aside). **Clarified by the user:** menu navigation itself isn't the problem — a segment built around navigation is fine as long as the speaker is actually reacting to or engaging with something of substance somewhere in it; the defect is a segment that's *only* setup/navigation with no genuine reaction anywhere. Added a prompt rule reflecting that distinction (`analyze.ts`). Not yet re-verified against a fresh render.

## Resolved

- **Transcription hint hallucinated an opening sentence.** When the source video's title+description was first fed to WhisperX as Whisper's `initial_prompt` (2026-09-02), the transcript came back opening with a full sentence that was never spoken in the audio. Cause: the hint was truncated to a fixed 600 chars, landing mid-clause, and Whisper treats `initial_prompt` as text immediately preceding the audio, so it "continued" the dangling sentence. Fixed by trimming the hint back to the last sentence-ending punctuation (`buildTranscriptionHint` in `videoContext.ts`) so it always reads as finished text. Re-verified: hallucination gone, the proper-noun spelling improvements (a content name and a person name) retained, no prompt phrases leaked into the transcript.
- **Mid-word clip cutoffs.** Fixed word-index → timestamp mapping added no trailing buffer, so clips could end mid-word. Fixed with a fixed end-padding constant, then a dynamic two-tier padding (quick-cut vs. genuine-sentence-end) driven by a new `endsAtSentenceEnd` flag from the analyzer. (`0abd7e2`, `9fc539d`)
- **Subtitles pre-displaying next sentence during a pause.** `getVisibleWords()`'s fallback logic centered the display window around an upcoming word during silence. Rewritten to never show future words and to clear entirely when the pause exceeds a threshold. (`9fc539d`)
- **Titles latching onto unshown trailing content.** A segment cut off right as a new topic was introduced, and the title generator built its title around that unshown tease. Fixed by threading the analyzer's `endsAtSentenceEnd` flag into title generation with an explicit caveat when true. (`600d3cd`)
- **Clips ending mid-sentence on stutters/false starts.** The analyzer's transcript had no pause information, so a repeated false start ("I'd probably be I'd probably be") followed by silence looked like a valid ending. Fixed by adding inline pause-length markers to the transcript and an explicit prompt rule about false starts. (`a7ee025`)
- **Titles keying off closing-line details not covered elsewhere.** Even on segments that ended at a genuine sentence boundary, the title generator kept building titles around whatever the last sentence mentioned. Fixed with a general prompt rule to base the title on what's substantially discussed across the clip, not just its ending. (`6c72601`)
- **Segment boundaries overshooting a few seconds into the next topic.** Sparse word-index markers (every 20 words) gave the analyzer LLM too much interpolation error. Halved the marker interval to 10 and added a prompt rule to prefer ending early over overshooting. (`421f07e`)
- **Subtitle flashing / boundary overshoot, root cause.** Traced to Whisper forced-alignment failures producing degenerate timestamp runs (e.g. 10 words crammed into 0.2s) — this both broke subtitle timing directly and corrupted the analyzer's word-index interpolation. Added timestamp-burst normalization in `transcribe.ts`, plus a code-level "snap to nearest real pause" backstop in `analyze.ts` for genuine-sentence-end segments. (`49c88d0`)
- **Segments still ending mid-clause ("...clicks that are").** The `endsAtSentenceEnd: false` prompt wording was ambiguous enough that the LLM read it as license to end mid-sentence. Reworded the prompt to make clear both cases require a complete clause, and added a code-level dangling-word blocklist backstop that pushes the boundary forward. (`8b4dab6`, first pass)
- **Dangling-word blocklist was whack-a-mole.** The blocklist caught "are" but missed "I'm" (a contraction), and after adding contractions the next clip ended on "actually" (an adverb no reasonable blocklist would cover). Replaced the word-list approach with a general one: Whisper's transcript already attaches punctuation to words, so the boundary now extends forward until it lands on a word carrying real clause-ending punctuation. (`8b4dab6`, final)
- **Transient Groq `json_validate_failed` errors.** The analyzer's Groq call occasionally returned a 400 with an empty `failed_generation`, observed correlating with a tight remaining-token budget on the free tier's 8000/min cap during rapid back-to-back test runs. `groq-sdk` doesn't retry 400s on its own; added explicit retry-with-backoff. (`8b4dab6`)
- **Subtitle flash missed by burst-detection (isolated + overlapping timestamps).** The burst detector only caught runs of 3+ near-zero-duration words with near-zero gaps; missed an isolated single-word glitch and out-of-order/overlapping word timestamps (a word starting before the previous one finished). Replaced with a simpler two-pass fix: clamp overlapping starts forward, then floor every word to a minimum plausible duration. (`e691404`)
- **Doubled/distorted render audio.** `ShortClip.tsx` renders the same video source twice (blurred background + centered foreground) with neither muted, so Remotion mixed the same audio track into itself twice. Muted the background layer. (`e691404`)
- **Render audio quality not guaranteed to match source.** `downloadSegment()` had no explicit format selector. Made it explicit (`bestvideo*+bestaudio/best`) so it can't silently pick a lower-quality combined format, independent of the separate downsampled audio-only pass used only for transcription. (`e691404`)
- **Whisper hallucinating a phrase onto unclear audio.** Unintelligible audio at a clip's start got transcribed as a near-duplicate of a genuine phrase said ~20s later, leaving the real occurrence with no subtitle. Confirmed via Groq's segment-level confidence data (`avg_logprob`, `no_speech_prob` — only returned when `timestamp_granularities` explicitly includes `'segment'`, not just `'word'`): the hallucinated segment's confidence was notably worse than normal. Words in low-confidence segments are now dropped rather than trusted. (`a2e75a8`)
- **Subtitle groups mixing words from different sentences.** Groups only split on a >0.5s pause or the 4-word cap, so back-to-back short sentences with little pause between them (e.g. "the hardest. Right. Crypt") got merged into one on-screen group. Groups now also always break after sentence-ending punctuation. (`a1250cf`)
- **Boundary-extension accepted a comma as a good enough stopping point.** A clip ended mid-sentence on a word carrying only a comma, which reads as a random cutoff despite technically carrying punctuation. Restricted the check to real sentence terminators (`. ! ?`) only. (`a1250cf`)
- **Sliding-window subtitles "repeating themselves."** The original display kept the trailing N most-recently-spoken words on screen at all times, so already-shown words got carried over and re-displayed alongside new ones as the window advanced. Replaced with precomputed, non-overlapping groups. (`c0fc286`)
- **Dangling-word extension cap too small.** The 12-word budget for finding real sentence-ending punctuation wasn't enough for some longer unpunctuated stretches, so it could still land on a dangling word ("to") once exhausted. Raised the budget to 20 and added a backward-search fallback that trims the clip shorter rather than accepting an incomplete cut. (`8309dd9`)
- **Duration-cap trim undoing the sentence-end fix.** The 60s duration cap was enforced by decrementing word-by-word *after* the sentence-end selection ran, which could walk straight back through a good ending and land on a dangling word again (a clip ended on "Bear" mid-phrase). The trim now re-searches for real sentence-ending punctuation once it's found a duration-fitting index, instead of just stopping wherever raw truncation lands. (`3b128b2`)
- **Segments straddling two unrelated topics.** A segment had clean sentence boundaries on both ends but covered the tail of finishing one thing and the start of an unrelated one, with no real throughline. Added a prompt rule steering the analyzer to keep a segment within one coherent moment. (`b87987d`)
  - **Recurrence (2026-09-15):** the prompt rule alone didn't hold on a new case — a segment covered the speaker quitting one level for the day and, moments later, opening a completely different level, with no long pause at the seam to make it obvious. The title compounded it by narrating both beats as one story (naming the level being quit as if its song was playing during the newly-opened level), and the segment's second half had no real content either — just menu navigation and an announcement, cut off before any gameplay. User verdict: reject the clip, nothing usable happens in it. Strengthened the existing prompt rule with an explicit "no long pause required" example (see `analyze.ts`), and added a new rule requiring a segment to contain an actual moment rather than just setup/transition — see the new Open entry below. Same "free model doesn't reliably follow a prompt rule alone" pattern as the dead-air case above; watch whether this needs the same deterministic-code-backstop treatment if it recurs again.
- **Hallucination filter blanking out a long stretch of real speech.** The confidence-based word-dropping added for the earlier hallucination bug worked as designed on an isolated case, but on a longer stretch, three separate low-confidence segments (with small genuine silences between each) all got dropped, leaving 26s of dead subtitles despite continuous speech. Capped dropping to a single contiguous low-confidence stretch of at most 6s — merging nearby (not just overlapping) low-confidence ranges first, since the three segments here were close together but not literally touching. A short hallucination still gets dropped; a long unreliable stretch is now shown (imperfect) rather than blanked. (`6d088c9`)
- **Whisper transcribes the same phrase twice — once as a near-zero-duration burst, then again normally-paced.** A clip's subtitles flashed through several words in under a second with no matching audio, then later showed the same words again correctly when actually spoken. Root cause confirmed via raw transcript inspection (2026-08-26): Whisper emitted a 10-word phrase crammed into 0.28s (~0.02s/word, physically impossible), then emitted the same phrase again ~5s later at a normal pace — a genuine duplicate/hallucination, not a timing-drift issue. The existing floor-and-cascade normalization didn't detect or drop this kind of run, so the burst still rendered, just spread across ~1s instead of ~0.3s. Added `dropDuplicateBursts()` in `transcribe.ts`: detects a contiguous run of 3+ words with near-zero original duration and near-zero gaps, and drops the whole run — while leaving an isolated single near-zero-duration word alone (that's a one-off glitch, not a duplicate, and is what the existing floor/clamp already handles). Verified against the exact case that surfaced it.
- **Segment cut lands on the video's actual real position rather than an estimated byte offset.** Directly tested (2026-08-29): a requested extraction range (e.g. `233.3s-259.0s`) sometimes came back containing content from significantly later in the source video (up to ~15s off, the offset varying by position — not a fixed skew). Traced to `downloadSegment()`'s use of yt-dlp's `--download-sections` on a video that fell back to a non-fragmented progressive-HTTP delivery format (surfaced by a wall of `[GetPOT]` token-fetch warnings) — for that format, `--download-sections` estimates a byte offset for a given timestamp, and that estimate drifts when the video's real bitrate varies, in a way it doesn't for YouTube's normal fragmented/DASH delivery. Fixed by no longer trusting yt-dlp's section-estimate for the final cut at all: `downloadFullVideo()` now fetches the whole video once, and a new `extractSegment()` trims the exact range locally with ffmpeg (`-ss` before `-i` for a fast keyframe-adjacent seek, then re-encoding for a frame-accurate true start) — accurate regardless of the source format tier. Verified by re-testing the exact previously-offset range and confirming it now lands at true 0.00s.
- **Whisper's word-level timestamps carry several-second-scale error, unrelated to how long the audio handed to it is.** The most consequential bug chased this project: a clip's actual audible content could run several real seconds past where the analyzer intended to stop — not a display-timing nuisance, but the clip covering the wrong stretch of the real video, discovered when a clip audibly cut off mid-word, several sentences past its intended end, despite the analyzer choosing a clean sentence boundary by word index. Multiple theories were tested and ruled out before finding a real fix:
  - *Whisper's ~30s internal chunk boundary* — refuted (2026-08-26): checked every segment boundary and duration anomaly across a full video against every 30s mark; offsets ranged ±10s with no clustering near zero.
  - *Anchoring words to Whisper's own segment boundaries* — tried and reverted (2026-08-26): those boundaries turned out to often include several seconds of unspoken silence padding, so force-stretching words to fill them introduced new, different desync.
  - *Splitting the audio into short, independently-transcribed chunks with a known additive offset* — tried and reverted (2026-08-31): didn't meaningfully reduce the error even at 30s chunks. Testing (a tight 15s extraction transcribed standalone) showed the error wasn't really about how much audio Whisper had processed *before* reaching a word — three different "should be accurate" measurements of the same reference word disagreed with each other by up to ~4s, pointing to inherent imprecision in Whisper's own attention-based word timing rather than a cumulative-depth effect chunking could fix.
  - **Actual fix: switched transcription from Groq's hosted `whisper-large-v3` to a locally-run WhisperX pipeline** (`whisperx_transcribe.py`, invoked as a subprocess from `transcribe.ts`, running on the project's own GPU via a dedicated `whisperx-venv/`). WhisperX exists specifically to fix this class of problem: it still uses Whisper for transcription, but re-times every word with a dedicated wav2vec2 phoneme-alignment model run directly against the audio, instead of trusting Whisper's own attention weights. Verified directly against the same reference case: the word that was ~3.6s off under Groq landed within ~0.03s of the tightly-scoped ground-truth position under WhisperX, on the same full, unchunked video — and the real boundary computation shifted by 5.3s as a result, moving the clip's actual end from several sentences too late back to the intended stopping point. Confirmed end-to-end on a real rendered clip: sync and ending both held up (user-confirmed, 2026-08-31).
  - **Side effect:** transcription no longer depends on Groq's API at all (analysis and title generation still do), which incidentally closes most of the [unattended job resilience](backlog.md#unattended-job-resilience--needed-before-this-can-run-without-a-user-present) gap for this specific step — no more rate-limit exposure for transcription specifically.
  - **Known gap left by this fix:** the Groq-era confidence-based hallucination-dropping mitigation isn't currently ported to the WhisperX path (see Open above).
